Sound and control are separate

Three switches, not one. Leave the ones you do not need off. What each one opens.

Sharing a screen is not
blanket permission.

Sound, your voice, and control of the machine are three separate decisions, each made before the session starts. One of the three has a recorded LAN pass behind it; the other two are in the build but untested on hardware.

Computer audio Available

The sending PC’s own sound travels with the picture. A Windows viewer decoded it in the LAN run; audible output on a phone was not independently confirmed.

Microphone voice Preview

Your own voice, two ways. Sharing a screen never needs it. The code builds and passes its checks; nobody has done a physical round-trip or echo test.

Remote input Preview

Permission for the watching device to drive the mouse and keyboard. That is no longer watching. Physical input, and behaviour inside native games, are unproven.

Hardware and Windows permissions still apply on top of these switches. These statuses match the ledger below, not a later git checkout.

Sending and watching

In the public Windows and Android builds. If a physical run is still missing, the same line says so.

Screen and window capture
Available
Share an entire screen, or pick a single window, from a Windows x64 PC.
Video quality controls
Available
Choose 60 or 30 fps and adjust stream quality while a session is running. Those controls do not promise sustained 60 fps on every PC.
H.264 encoding
Available
NVIDIA NVENC is the validated path. Other PCs fall back to the built-in Windows CPU encoder, which costs processor time. Vendor hardware acceleration and physical Intel/AMD streaming tests are still pending.
Android receiving
Available
Android 8 or newer, decoding in hardware. Validated on one device in the public 0.3.2 Preview 2 run.
Windows receiving
Available
A second Windows PC can receive the screen and system audio. Both ends need matching builds.
Computer audio
Available
The sending PC’s audio travels with the screen. The receiver decoded computer audio in the LAN run with no reported underruns. Audible output on a phone was not independently confirmed.

Ships. Unproven.

The control is in the UI. Nobody has signed off a physical test. That is Preview, not Available.

Private session admission
Preview
The viewing device issues a private invitation that authorises the session over a pinned QUIC connection. Expiry, replay, and revocation pass loopback tests; physical regression testing is still open.
Two-way microphone voice
Preview
Builds and passes its checks. Physical round-trip and echo testing have not been done.
Remote control from Android
Preview
Builds and passes its checks. Physical input, and behaviour inside native games, are unproven.
Cursor appearance and effects
Preview
Desktop cursor styling with a local effects budget. The current build labels this preview only.

Needs something you already run

We do not sell you a cloud for this. Off-LAN viewing needs a route you already have. Contacts stay on the PC.

Viewing outside your local network
Limited
Works across a private mesh you already run. STUN probing is implemented; automatic universal Internet traversal is not. A reachable route has to exist first.
Device-owned accounts and contacts
Limited
Held locally on Windows. Sync, recovery, and global handle claims are not implemented.

Not in this download

Do not look for these in 0.3.2 Preview 2.

Automatic update checks
Not yet
Present in some development builds, not in this download. Update by installing a newer matching Windows and Android pair over the old one.
Managed relay and multi-viewer rooms
Not yet
There is no FastCast-run media relay, and multi-viewer rooms are not implemented.
Linux desktop
Not yet
Not in these public files. Application source has a Linux viewer (OpenH264, optional VA-API). Linux send is not a product.
macOS, iPhone, and iPad
Not yet
Not implemented. This preview download is Windows x64 and Android 8 or newer only. Android does not send.

One LAN run on these files

Exact 0.3.2 Preview 2 Windows host and Android APK

  • 120.032 seconds over LAN
  • 5,925 encoded frames and 5,924 rendered frames
  • One video reassembly drop, recovered in 229 ms
  • Computer audio decoded with no reported underruns; audible output was not independently confirmed
  • Variable-cadence test source averaged 49.35 rendered fps

Observed in one physical Windows-to-Android LAN run. Evidence, not a universal performance guarantee.

  • This does not validate sustained smooth 60 fps.
  • Six capture recreations caused presentation gaps over 200 ms, longest 285 ms.
  • Audible playback, a 30-minute endurance run, physical remote input, and unrelated-network media remain unqualified.
