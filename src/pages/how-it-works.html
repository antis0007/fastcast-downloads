01 / Direct media path

  1. Your Windows PC

    Capture & encode

    Your selected screen or window becomes compressed video. Enabled computer audio travels with the session.

  2. Encrypted QUIC over UDP

    Peer to peer

    Across your LAN, or through a reachable internet or private-network route.

    The {{PRODUCT}} relay carries no media on this path.
  3. Windows or Android

    Decode & display

    The viewer rebuilds the picture and plays the audio. Your devices do the media processing.

Direct describes the endpoints.

Wi-Fi access points, routers and an internet provider can still carry the packets. “Direct” means {{PRODUCT}} does not forward the session through its media relay. Discovery and pairing services may still help the devices find each other.

02 / Relayed media path

  1. Your Windows PC

    Capture & encode

    The sender still makes the video and encrypts the connection. The relay does not encode your screen.

  2. {{PRODUCT}} media relay

    Receive & forward

    When a direct connection cannot be established and both peers obtain a relay allocation, packets travel through this service.

    The media connection remains encrypted between the devices.
  3. Windows or Android

    Decode & display

    The viewer is still the endpoint that decrypts and plays the stream. The relay sees traffic, not the decoded picture.

Relay capacity and network limits

The relay uses server bandwidth and can add delay. Availability and capacity matter; it is not a guarantee that every network connects. This preview’s relay path also uses UDP, so it does not solve a network that blocks UDP entirely.

Before the first frame

How a session
is established

An address says where a device might be reachable. An invitation carries the information needed to join it. The connection still has to succeed.

  1. 01 / Invitation

    Choose the other device

    To set up screen sharing, the viewing device creates an invitation and the sending PC imports it. Share it privately: it includes connection and session credentials. Screen sharing does not require an account; friends and calls use a device-owned account.

    Follow the setup steps →
  2. 02 / Discovery

    Find possible routes

    The app gathers local addresses, asks a STUN service what public address it sees, and requests a temporary router port mapping where supported. A pairing service exchanges encrypted connection information between the peers.

  3. 03 / Connection

    Try the path & verify the peer

    The peers try to reach each other, including coordinated UDP connection attempts. The invitation’s certificate identity and session proof protect admission. If direct setup fails, an available relay offers another UDP path.

  4. 04 / Media

    Agree on playback

    The sender and viewer agree on a compatible video format. Capture, encoding, transmission and playback begin. A route can connect successfully yet perform poorly if the devices or network cannot keep up.

Why the same app works on one network and fails on another

A home router usually shares one public address among several devices. NAT is the translation between their private addresses and that public address. A temporary port mapping or coordinated outbound packets can make a return path possible, but router and firewall policies differ.

STUN discovers an address; it does not relay your screen or open a firewall. UPnP, NAT-PMP and PCP are ways to request a router mapping. Guest Wi-Fi isolation, restrictive NAT, VPN policies and blocked UDP can still prevent a connection. An HTTPS helper being reachable proves only that small setup messages can reach it.

The current receiver starts discovery automatically, using {{PRODUCT}}’s STUN service first, with Cloudflare and Twilio fallbacks. The public preview has no setting to disable those automatic discovery requests. See the discovery disclosure or troubleshoot a connection.

Capture & compression Windows Graphics Capture · NVENC · H.264 / HEVC / AV1 · Opus

Capture obtains frames from the screen or window you select through Windows Graphics Capture. Encoding compresses those frames before they leave the PC. NVIDIA NVENC is the hardware encoder path; a Windows CPU H.264 encoder provides a compatibility fallback at the cost of processor work.

H.264, HEVC and AV1 are video formats, not connection types. The automatic choice depends on both the sender’s available encoder and the receiver’s advertised decoding support. Windows receiving uses H.264; eligible Android hardware can negotiate HEVC or AV1. A newer format is useful only when both ends can run it well.

Computer audio uses Opus, an audio codec suited to interactive sound. Windows audio capture/playback uses WASAPI; Android playback uses AudioTrack. Microphone and remote-input controls remain separate from screen selection.

Higher resolution, frame rate or bitrate can demand more encoding work, network capacity and decoder capacity. An available codec is not a guarantee of a particular frame rate or visible quality.

Technology references: Windows screen capture · Opus.

Transport & recovery QUIC over UDP · reliable streams · video datagrams

UDP carries packets between the devices, directly or through the relay. QUIC adds an encrypted connection, congestion handling, and different ways to deliver data. {{PRODUCT}} uses Quinn for QUIC and rustls for its TLS security.

Video uses QUIC datagrams: a late or missing packet does not force every newer video packet to wait for its retransmission. This favors freshness, but losing part of a frame can make that frame unusable. {{PRODUCT}} adds recovery information and can request a fresh decoding reference when needed. Computer audio travels on a reliable stream; that protects delivery but does not remove the need for timely playback.

FEC means forward error correction: extra recovery data can reconstruct some lost data without waiting for a resend. It consumes additional bandwidth and has limits. Pacing spreads packet transmission over time; receiver buffering absorbs some arrival variation. More buffering can smooth playback while adding delay.

QUIC alone does not guarantee NAT traversal, 60 fps, loss-free playback or uninterrupted switching between networks. This release has no TCP media fallback when UDP is blocked.

Technology reference: Quinn’s streams and datagrams.

Identity & encryption Invitation-bound peer identity · TLS · session admission

The invitation binds the expected peer certificate to the session. The connection verifies that identity and requires the session’s admission proof before media is accepted. An address alone is insufficient to join.

The screen-sharing connection uses QUIC’s TLS encryption between the devices. The UDP relay forwards the encrypted packets rather than terminating that peer connection. Pairing is a separate exchange: the route payload is encrypted using a secret shared through the invitation.

Those protections depend on keeping the invitation private and trusting the receiving device. They do not conceal all connection metadata, prevent screenshots on the viewer, or establish that the preview has passed an independent security audit.

Playback & the native apps Rust · Windows media components · Kotlin / Android MediaCodec

Rust owns the shared networking and media core. The Windows application uses a native Rust desktop interface; the Android app combines Kotlin platform UI with that Rust core. The browser serves this website, not the screen-sharing session.

On the viewer, compressed video must be reassembled, decoded and presented at the right time. Windows uses its media components; Android uses MediaCodec and the device’s available decoder. Decoder compatibility, screen refresh rate, thermal limits and audio output all affect the result.

Latency is the sum of capture, encoding, network travel, buffering, decoding and presentation. A fast connection does not make the other stages free. Conversely, a decoder accepting a frame does not prove that the screen displayed it smoothly or that a speaker played the audio.

Technology reference: Android MediaCodec. For this release’s actual evidence, see release notes.
